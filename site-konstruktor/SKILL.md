# Сайт-конструктор

**Версия скилла: 1.0** (журнал изменений в конце). При каждой правке поднимай номер и дописывай строку в журнал.

Скилл ведёт пользователя от идеи до первой настоящей продажи на своём сайте: домен → Yandex Cloud → сайт → документы → РКН → платёжка → сервер выдачи → боевой запуск. В основе — реальный запуск продукта (программа для Windows, бессрочная лицензия, самозанятый, Робокасса) со всеми ошибками. Справочники — в `references/`, шаблоны — в `templates/`.

## Главный принцип

**Максимум делает Claude. Пользователь — только то, что может сделать лишь он.**

Каждый шаг заранее помечается:
- **[C]** — делает Claude: код, тексты, документы, автотесты, скрипты, выкладка и инфраструктура через `yc`, проверки, архив;
- **[П]** — только пользователь: регистрации и оплаты, идентификация (Госуслуги), договоры, подачи в РКН и платёжку, входы и 2FA, подтверждение входа `yc` в браузере, капчи, окна UAC, создание и хранение секретов, ввод секретов в переменные функции, платежи/возвраты/пополнения, необратимые решения.

Если сомневаешься, кто делает шаг, — сначала проверь, можешь ли ты (инструменты, доступ к ПК, `references/claude-env.md`), и только потом отдавай пользователю.

## Команды

| Команда | Что делает |
|---|---|
| `Сайт-конструктор` | Новый проект: анкета → карта фаз → первая фаза |
| `Сайт-конструктор: продолжить` | Читает `project-state.md` проекта, продолжает с первого незавершённого шага |
| `Сайт-конструктор: статус` | Кратко: фазы и статусы, чего ждём, ближайшие сроки, открытые хвосты |

## Старт нового проекта

1. Задай анкету **одним сообщением** (через инструмент вопросов с вариантами, где он есть; остальное — свободным текстом):
   - что продаём (программа / файл / доступ / услуга / физический товар);
   - цена и модель (разово / подписка / пробный период);
   - правовая форма (НПД / ИП / ООО);
   - как выдаём (ключ / файл / доступ / вручную);
   - языки сайта;
   - что уже есть (домен, облако, платёжка, документы, дизайн);
   - сроки и сколько времени в неделю есть у пользователя;
   - чего точно не надо.
2. Честно скажи, какие фазы опыт **не покрывает** для этого случая (`references/00-start-decisions.md`, таблица товаров). Для физического товара, услуги, подписки, ИП/ООО — назвать, что придётся проверять по источникам заново, и ничего не выдумывать.
3. Создай `project-state.md` из `templates/project-state.md`. Где хранить: в архиве проекта (если у пользователя есть скилл архива чатов — в его папке) и копией в рабочей папке проекта на ПК, если она подключена.
4. Покажи карту фаз с пометками [C]/[П] и ориентиром по срокам (в опыте ~3 недели от домена до первой оплаты, из них ожидания: делегирование до суток, модерация платёжки ~5 дней, реестр РКН до 30 дней).

Порядок гибкий: пока идут ожидания (делегирование, модерация, реестр), двигай параллельные фазы. Но жёсткие зависимости соблюдай:
- документы и сайт без заглушек — **до** заявки в платёжку;
- уведомление РКН — **до** первого заказа с почтой покупателя;
- резервное копирование — **до** первой настоящей оплаты;
- `RK_TEST=0` в функции — **до** `data-pay="on"` на сайте.

## Цикл каждой фазы

1. **Прочитай справочник фазы** целиком.
2. **Проверь актуальность** (WebSearch / WebFetch): цены, интерфейсы консоли, требования платёжки, законы (лимит НПД, 152-ФЗ, реклама, подпись кода). Опыт — на конец 2026 года, это ориентир, а не истина. Расхождения покажи пользователю одной-двумя строками.
3. **Сделай своё [C]**: код, тексты, скрипты, значения для форм. Шаблоны — из `templates/`, с подстановкой данных проекта; после подстановки найди оставшиеся `{{` — их быть не должно.
4. **Веди пользователя по его шагам [П]** — по одному шагу в сообщении (формат ниже). Жди «готово» или скриншот.
5. **Проверь результат сам**, не верь на слово: `?r=setup`, `yc … list`, журнал скрипта, WebFetch страницы, заголовки письма, скриншот.
6. **Обнови `project-state.md`**: статус, ID ресурсов (без секретов), даты подач и сроки ожидания, хвосты, напоминания.
7. **Отчитайся коротко**: что готово, что ждём и до какого числа, следующий шаг.

Для сроков (проверить реестр РКН, ужесточить SPF/DMARC, проверить делегирование) — предложи напоминание через доступные инструменты планирования.

## Формат шага для пользователя

```
Шаг N из M — <что делаем> [П]
Где: <сайт / программа> → <меню> → <пункт>
Что сделать: <1–3 действия>
Что вписать: <значения без секретов; для секрета — «из менеджера паролей, запись X, поле Y»>
Признак успеха: <что должно появиться>
Напиши «готово» или пришли скриншот.
```

Если у пользователя есть свой скилл пошагового ведения — следуй его стилю. Если он работает с телефона, шаги, требующие ПК, собирай в пакет «когда будешь у ПК».

## Обязательные правила

1. **Секреты.** Никогда не проси, не выводи и не сохраняй (чат, архив, облачный диск, память, репозиторий, журналы). Не запускай команды, печатающие токены и ключи (`yc config list` и подобные); переменные функции проверяй только по именам и несекретным значениям. Секреты генерирует пользователь (менеджер паролей) или скрипт с записью в буфер обмена. Закрытые ключи и копии базы с ПД — не на Google Диск и не в зарубежные облака.
2. **Деньги и необратимое.** Платежи, возвраты, пополнения — только пользователь. Удаление чего-либо — только после явного «да» с перечнем, что удаляется.
3. **Порядок включения оплаты.** Сайт с живой оплатой выкладывается только скриптом-предохранителем (`templates/scripts/_claude_pay.cmd`), который проверяет `RK_TEST=0` в функции.
4. **Честность сайта.** Никаких выдуманных отзывов, цифр, «прессы». Способы оплаты на сайте = способы на реальной странице оплаты. Возможности товара — только реальные.
5. **Модерация.** Пока платёжка проверяет магазин — не менять видимое модератору и DNS. Никаких заглушек.
6. **Только российские сервисы для ПД.** Иначе — трансграничная передача, отдельное уведомление РКН и риск запрета (`07-rkn.md`).
7. **Сервер.** Каждая версия — с автотестами (`templates/server/tests`), номер растёт, в архиве проекта — что изменилось и как развернуть. Обязательный список безопасности из `09-backend.md` не урезается.
8. **Переменные функции.** Каждая инструкция их правки включает «прикрепи zip ещё раз» (грабля № 5).
9. **Проверять в облаке, а не по коду.** Таймеры, правила хранения, ACL, режим оплаты — командой или `?r=setup`.
10. **Не юрист.** Документы и формы РКН — образцы. Ответственность за юридическую правильность — на пользователе; предложи сверить с юристом или образцами Контура / Гаранта.
11. **Инструменты.** Перед дизайном и оформлением — подбери и согласуй инструменты (если у пользователя есть скилл подбора — запусти его). Дизайн сайта — дизайн-скиллом, если он установлен. Чужие скиллы не ставить без проверки пользователем.
12. **Без лишних агентов.** Субагентов предлагай одной строкой с объяснением и запускай только после согласия.
13. **Конец сессии.** Обнови `project-state.md`; если у пользователя есть скилл архива чатов — предложи обновить архив.

## Чего скилл не делает

- Не подаёт заявления и не входит в аккаунты за пользователя.
- Не обещает одобрения платёжки и не гарантирует юридическую чистоту документов.
- Не ведёт физические товары, услуги и подписки «по опыту» — для них только проверка по источникам с явной пометкой.
